# Backend и Worker: договор взаимодействия

Этот документ задаёт общий формат работы Backend и Worker с PostgreSQL, Redis и MinIO. Если формат задания меняется, обе стороны обновляют реализацию вместе.

## Кто за что отвечает

| Сервис | PostgreSQL | Redis | MinIO |
|---|---|---|---|
| Backend | Создаёт задания и outbox-события, читает статус и результат. | Публикует задания в поток. | Принимает пользовательские файлы, сохраняет их метаданные. |
| Worker | Читает задания и нужные данные; записывает статус, результат и результаты обработки. Не изменяет земельные участки и права. | Читает задания, подтверждает обработку. | Читает переданные входные файлы и сохраняет результаты обработки. |

PostgreSQL — источник истины о задании и его статусе. Redis доставляет уведомление о задании, но не заменяет запись в БД. MinIO хранит содержимое файлов; в PostgreSQL хранятся ссылки и метаданные.

## PostgreSQL

Backend подключается к базе из `POSTGRES_DB` под `APP_DB_USER` и `APP_DB_PASSWORD` (роль `app_rw`). Worker использует `WORKER_DB_USER` и `WORKER_DB_PASSWORD` (роль `worker_rw`). Привилегированную учётную запись PostgreSQL нельзя использовать в приложениях.

### Создание задания

Backend в одной транзакции:

1. Добавляет строку в `platform.job` со статусом `queued`, типом задания, параметрами и UUID.
2. Добавляет в `platform.outbox` событие типа `job.queued` с тем же UUID задания.

Так задание и событие не разойдутся, если процесс Backend завершится между записью в БД и отправкой в Redis. Компонент Backend, публикующий outbox, добавляет сообщение в Redis Stream и после успешной публикации заполняет `published_at`. Повторная публикация допустима.

Для строки outbox договорились о значениях: `aggregate = 'job'`, `aggregate_id = job.id`, `type = 'job.queued'`, `payload = {"job_id":"<UUID>","type":"<job.type>","event_version":1}`.

`platform.job.params` — источник параметров задания. Сообщение Redis содержит только идентификатор и тип; Worker загружает актуальные параметры из PostgreSQL. Формат `params` согласуется отдельно для каждого `type`.

### Статусы и результат

Согласованный путь задания:

```text
queued -> running -> succeeded
                  -> failed
queued -> cancelled
```

Worker увеличивает `attempts` при начале обработки, выставляет `started_at`, а при завершении — `finished_at`. В `result` Worker сохраняет результат либо структурированную ошибку, например:

```json
{
  "error": {
    "code": "INPUT_NOT_FOUND",
    "message": "Input object was not found"
  }
}
```

`failed` в первой версии — конечный статус; повторный запуск оформляется Backend как новое задание. Backend не должен считать задание выполненным до `succeeded` и не должен перезаписывать результат Worker.

Worker имеет доступ только к схемам и действиям, выданным `worker_rw`; новые права добавляются отдельной SQL-миграцией, не расширением учётной записи Worker.

## Redis

Используем Redis Stream `cago:jobs` и consumer group `cago-workers`. Backend публикует событие только после фиксации транзакции PostgreSQL. Идентификатор записи `platform.outbox.id` используйте как поле `event_id`, чтобы отслеживать повторную публикацию.

Формат сообщения Stream:

```json
{
  "event_version": 1,
  "event_id": "123",
  "job_id": "UUID",
  "type": "satellite.process_scene"
}
```

Backend создаёт consumer group при инициализации publisher, не Worker. Worker читает новые сообщения через consumer group, используя уникальное имя consumer для каждого процесса. После записи конечного статуса в PostgreSQL Worker подтверждает сообщение командой `XACK`. Сообщение может доставляться повторно: обработчик обязан проверить статус задания и быть идемпотентным по `job_id`. Уже завершённые или отменённые задания повторно не обрабатываются.

В первой версии автоматический повтор при ошибке не выполняется: Worker сохраняет `failed` и подтверждает сообщение. Если Worker завершился аварийно до подтверждения, запись остаётся в pending entries list; восстановление такой записи и признание прерванного задания неуспешным выполняет Worker при запуске, затем подтверждает сообщение. Параметр времени, после которого разрешено считать обработку прерванной, должен быть больше максимальной длительности задания.

Backend использует Redis-пользователя `cago-backend` и `REDIS_BACKEND_PASSWORD`; Worker — `cago-worker` и `REDIS_WORKER_PASSWORD`. Redis ACL сейчас разрешает обоим пользователям ключи с префиксом `cago:`. Не используйте административную учётную запись для приложений.

## MinIO

Для разработки используйте bucket `cago-docs`, созданный Compose. Backend подключается с учётными данными `MINIO_BACKEND_USER` и `MINIO_BACKEND_PASSWORD`; Worker — `MINIO_WORKER_USER` и `MINIO_WORKER_PASSWORD`. Root-учётные данные MinIO предназначены только для администрирования.

- Backend создаёт объект и строку `docs.file_object` с bucket, object key, именем, MIME-типом, размером и SHA-256. Имена файлов пользователей не используйте как object key; ключ должен быть уникальным и генерироваться приложением.
- Worker получает ссылки на входные объекты в параметрах задания, читает их из MinIO и сохраняет выходные файлы с отдельными object key. Worker не читает `docs.file_object`: такой доступ не выдан ролью `worker_rw`.
- В `platform.job.result` Worker возвращает ссылки на созданные объекты (`bucket`, `object_key`, а при необходимости `size_bytes` и `sha256`). Если выходной файл должен стать пользовательским документом, Backend создаёт для него запись `docs.file_object`.
- Не передавайте содержимое файлов через Redis или PostgreSQL. Не публикуйте bucket и не помещайте секреты в object key.

Обе учётные записи MinIO в текущем Compose имеют права `readwrite`; это доступ к объектному хранилищу для разработки. Для production права следует ограничить bucket `cago-docs` и разделить секреты по сервисам.

## Локальная проверка

Из корня репозитория запустите инфраструктуру:

```powershell
docker compose up -d --build
docker compose ps
```

Сервисы должны быть готовы (`healthy`, если для сервиса настроен healthcheck). В локальном запуске адреса: PostgreSQL `localhost:5433` (или порт из `POSTGRES_PORT`), Redis `localhost:6379`, MinIO `http://localhost:9000`. Внутри Docker-сети PostgreSQL доступен как `postgres:5432`; используйте имена сервисов `postgres`, `redis` и `minio`.

Перед интеграцией проверьте сквозной сценарий: Backend создаёт `platform.job` и outbox в одной транзакции; publisher отправляет событие в `cago:jobs`; Worker получает его, читает параметры из PostgreSQL и входной объект из MinIO; Worker сохраняет конечный статус и результат в PostgreSQL, затем подтверждает Redis-сообщение. Повторно доставленное сообщение не должно повторно создавать побочные эффекты.

Точные команды запуска и тестирования Backend и Worker добавляются в их README после появления соответствующих приложений.
